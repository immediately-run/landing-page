A capability is a narrow, revocable grant: a specific mount, a specific task contract, the identity handle. Your app starts with the mounts the host gave it and asks the user for anything more through host UI you do not draw.

## Requesting more access.

Need another space or folder? Call the SDK request method and the user picks in the host’s own picker. Note what the app does NOT get to say: there is no mode argument. The user chooses read-only or read-write explicitly, with no default, and picks a single project folder inside the space — so a shared space opens scoped to that project, never whole. Expect cancellation and absence — degrade the feature, do not crash.

<ApiSignature
  id="signature"
  toc="requestMount()"
  sig="requestMount(): Promise<SandboxMount>"
  cap="filesystem"
  capHref="/docs/capabilities/model"
  returns="A SandboxMount for the ONE project folder the user granted, chroot'd to it. Read the granted access off mount.mode — the user decided it, not you. Paths outside the project are unnameable; .. and absolute escapes are not addressable."
  params={[]}
  rejections={[
  { code: "cancelled", meaning: "The user dismissed the host picker." },
  { code: "forbidden", meaning: "Policy denies this app the filesystem capability." },
  { code: "auth-required", meaning: "The operation needs a signed-in user and there is not one." }
  ]}
/>

<Callout tone="warning" title="Writes to a read-only mount fail.">
  A grant may be read-only — and since the user picks the mode, assume it will be. Writing to a ro mount rejects with EROFS. Gate write affordances on `mount.mode` and re-evaluate on mount changes; never surface EROFS as UX.
</Callout>

## Typed errors everywhere.

Platform calls reply `{ ok: false, code, message }` with a small, stable set of codes: forbidden, auth-required, cancelled, invalid-params, timeout. Handle each by meaning, not by string-matching the message.
